## Review and dispatch contract

An authenticated human with project requester access proposes a bounded operation against a completed, non-cancelled run with failed/errored results and a protected `report.json`. The run must carry matching Jira Cloud source provenance from an approved read adapter at the same API base/project; synthetic fixture provenance cannot authorize writes. Source adapter/connection-scope revisions also bind the review. Create produces a standard issue using one configured issue type. Comment targets the original source issue or a defect successfully created for this run. Transition additionally requires exact operator mappings for transition ID/name and source/destination status IDs. It supports transitions with no required extra fields; custom create fields, attachment upload, arbitrary edits, notification controls, Data Center writes and MCP writes are unsupported.

Draft text contains only the operation ID, source key, safe test identifiers/statuses, evidence digest and the configured HTTPS protected-report URL. It excludes model-authored titles, descriptions, source text, actual values, screenshots, traces and customer payloads. Errors are investigation candidates, not proven product defects. Jira users still need separate QA Buddy access to open reports; there are no public or signed bearer links. Cross-system disclosure of these minimal identifiers still needs the organization's data-owner review and the capability's explicit approval reference.

A distinct live human project approver must review the exact destination, payload, configuration and evidence hash before approving. They must also differ from the run requester. Service/demo identities, eval grants and model/tool output cannot approve or invoke this capability. Approval lasts at most 15 minutes (default 10); it does not send anything. The same approver must separately dispatch once. The workspace's Results & evidence panel opens this review screen; the backend enforces the contract independently of UI controls.

The receipt binds the capability, project/tenant access policy, independently approved write host, workspace report origin, current write module bytes, dependency fingerprint, source/plan/results/artifact hashes and upstream target metadata. Audit projection bytes are excluded because recording review necessarily changes them. Reviewer/requester session or credential revisions, identity status, roles, capability, evidence, expiry and capacity are rechecked at dispatch and immediately after durable intent. Project/type or target/workflow metadata is read before proposal and again before dispatch. Changed timestamps/statuses or mappings require a new review; there is no conditional Jira transaction spanning this check and the write, so an upstream race remains possible.

## Configuration and operation

Start from [`config/jira-writes.example.json`](../../config/jira-writes.example.json). It is disabled review material, not loaded automatically. Bind the workspace project to the same Jira project key and tenant; choose a standard issue-type ID/name and workflow mappings after reviewing the organization's metadata and required fields. Configure a separate least-privilege write identity through server-side credential environment references. For scoped API tokens, the supported prefix is `https://api.atlassian.com/ex/jira/<cloud-id>`; otherwise use the approved HTTPS site root. Explicitly add that host to `config/policy.json` under `jira_writes.approved_hosts`. Never broaden `integration.http` or the read adapter's allowed methods.

Jira Cloud REST v3 uses [create issue and workflow transition endpoints](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) and [ADF comment bodies](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-comments/). This implementation uses fixed GET/POST routes, TLS verification, no redirects, no environment proxy inheritance and no HTTP retries. Each response is bounded to 256 KB and the request has socket/observed total deadlines; this is not an OS-level hard deadline or network sandbox. Required permissions and actual field/workflow/ACL behavior require an approved live sandbox test.

For API clients, all routes are under `/api/runs/{run_id}/jira-writes` and use existing authentication, tenant/run access and browser Origin/CSRF protections:

| Route | Behavior |
|---|---|
| GET collection | Read capability availability and at most 20 receipts |
| POST collection | Propose `{kind, target?, transition?}`; no arbitrary payload accepted |
| GET `/{operation_id}` | Read exact draft/hash/state/outcome, including after capability disablement |
| POST `/{operation_id}/review` | `{draft_hash, decision: approve or reject}`; exact distinct-human review |
| POST `/{operation_id}/dispatch` | Same approving human dispatches the approved draft once |

## Crash, duplicate and uncertain outcomes

SQLite schema version 2 adds the durable receipt table through the Store's existing transactional migration. Stop all old application instances before upgrading. The older version refuses this newer schema; rollback requires a compatible backup. Existing audit rows and artifacts remain intact. Backups include write receipts; restore moves every old receipt to `restored_reconciliation_required`, preserving drafts and the original audit history while invalidating dispatch authority. Reconcile Jira before bringing restored instances online. A historical success receipt alone cannot establish current upstream state after recovery.

Proposal fingerprints deduplicate the same run/evidence/operation/target/transition locally. Up to 20 proposals per run are retained. Independent SQLite connections serialize approval and dispatch with `BEGIN IMMEDIATE`. The operation enters `dispatching` with durable audit intent before the single POST. A successful, contract-shaped response becomes `succeeded`; **any unconfirmed result becomes `uncertain`**. Redirects, 429, auth errors, timeout, unexpected status/body and receipt-persistence failure do not trigger a retry. A process crash can leave `dispatching` indefinitely; startup never resets it. The create label `qa-buddy-<operation-id>` and comment operation ID aid manual lookup; they are not Jira-side idempotency keys.

For uncertainty, stop the original writer and verify it cannot still send, preserve its receipt/audit/evidence, and have an operator inspect the exact Jira target/history. Search the create label or comment operation marker as applicable. Record the upstream issue/comment/status and an independent reconciliation reference outside the application. There is deliberately no reset/retry endpoint. Do not propose a replacement from changed evidence, a new run or a restored database until reconciliation proves the intended next action is safe. This provides one dispatch attempt per local receipt, not exactly-once external mutation or global duplicate detection. Jira automations, concurrent writers, side effects, an upstream change after preflight and duplicate content from other runs remain organizational qualification work.

Audit and receipt updates commit together locally; filesystem projections and Jira do not share that transaction. Outbox backlog and evidence capacity gate dispatch, but OS/database/audit quotas, external immutable audit custody, protected service credentials, production network controls, deployment ownership and reconciliation procedures remain required. All implementation tests use synthetic data and mock Jira responses. No organizational issue was read or changed to develop this feature.
