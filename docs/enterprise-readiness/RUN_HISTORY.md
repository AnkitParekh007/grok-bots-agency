# Bounded run history

`GET /api/run-pages` returns `{items, next_cursor, limit}`. The default and maximum page size is 100; `limit` must be 1–100. Pass the returned opaque `cursor` to load older runs. The workspace's Sessions, Test Runs and Reports views provide Older runs / Latest runs controls; the recent sidebar remains on the latest page. Report filtering applies to the currently loaded run page, so a page with no completed runs can still have older reports. No global run count is implied by the displayed page.

The legacy `GET /api/runs` keeps its array response but is now bounded. Its `X-Next-Cursor` header provides continuation. Clients that need a full inventory must explicitly page instead of assuming one response is exhaustive. Existing individual run/report/artifact routes retain their access checks. API responses use the existing no-store policy.

Tenant, project and owner/approver authorization are expressed inside a constant SQL query with bound values before its row limit. This prevents unauthorized recent runs from filling the page and avoids loading all history into Python. The query returns at most 101 metadata rows, retaining the last one only to detect continuation. It orders by immutable creation timestamp and run ID to handle ties and newly inserted runs consistently. Cursor fields are length/type/format checked; a cursor is a position, not an authorization grant. A copied or modified cursor cannot expand the current caller's scope.

An index supports creation-time/ID ordering. Under the Store lock, the query has a two-second observed deadline and a SQLite progress callback every 1,000 instructions, refusing work beyond 2,000,000 instructions. The callback is removed on every exit before another operation can use that connection. Budget exhaustion returns 503 without a partial page or continuation claim. Time waiting for the Store lock, OS I/O stalls, other SQL, native workers and response delivery are outside this query budget. Large tenants with sparse permitted history still require workload/index qualification; the limit can expose that condition as an availability failure instead of unbounded work.

This is application admission work under ER-25. It does not supply retention/deletion/legal holds, OS/database/audit volume limits, tenant storage allocation, production scale or soak qualification. Trusted internal `Store.list_runs()` callers remain an unpaginated operator API; HTTP history no longer calls it. No historical evidence is removed by pagination.
